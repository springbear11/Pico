# 周期后台任务

## 用途

周期后台任务用于在正常测试流程运行期间，定时执行一个短小的插件 Action，例如：

- 每 5 秒发送一次 MODBUS 心跳；
- 定时喂看门狗；
- 定时刷新某个设备状态；
- 在挂测期间发送维持连接的协议报文。

它不是 Loop。Loop 会占住流程，循环结束后才执行后续 Step；周期后台任务登记后，正常 Main 流程会继续运行。

## 第一版执行方式

第一版采用调度线程协作式执行，不创建额外硬件调用线程：

```text
Setup 注册周期 Action
        ↓
主流程每个安全边界检查是否到期
        ↓
到期后申请 Action 所需资源
        ↓
资源空闲：执行一次；资源占用：延后
        ↓
生成新的 requestId，并安排下一周期
        ↓
Main 全部结束或 Stop：取消定时器
        ↓
进入 Cleanup
```

这种实现的重点是稳定：周期 Action 和普通 Step 不会同时进入同一厂家 DLL；已有资源事务区间仍然具有完整所有权；Session 结束时没有遗留线程或后台句柄。

## 资源规则

周期 Action 必须有可识别的独占资源：

```json
"resources": [
  { "resourceId": "MODBUS1", "mode": "exclusive" }
]
```

若 Action 使用固定 `inputs.deviceId`，可以省略上面的数组。编译器会把 `MODBUS1` 直接作为资源，把 `CAN1.CH1`、`CAN1.CH2` 统一归到设备资源 `CAN1`。

资源 ID 按设备层级互斥：`CAN1` 会与 `CAN1.CH1`、`CAN1.CH2` 冲突；两个完全不同的设备 ID 不冲突。这样旧脚本即使把事务区间写成通道 ID，也不会被设备级周期任务插队。

当普通流程通过 LOCK/UNLOCK 持有 `MODBUS1` 时，心跳到期也不会抢占。它会短暂延后，资源释放后再运行一次；延后的次数不会形成积压队列。

## 失败和停止

- 某次周期执行返回 Fail、Error 或 Timeout：记录 Attempt、日志和错误码，正常 Main 继续运行，最终 Session 为 `CompletedWithError`。
- Stop 或 Abort：不再启动新的周期调用，取消尚未到期的定时请求。
- 已经进入插件的同步调用：沿用普通 Step 的停止边界，等待插件返回；第一版不会强杀线程。
- Main 结束：先停止所有周期任务，再释放 Main 资源兜底，最后执行公共 Cleanup。

## 当前不支持

- 一个周期任务内包含多个 Step；
- 周期任务内嵌 TestItem、Loop、Barrier、MessageBox；
- 周期任务自身 Retry；
- 在调试 Pause 期间仍保持严格的墙钟周期；
- 某个同步 DLL 调用长时间阻塞时仍保证精确 5 秒触发；
- 多线程并行调用同一设备。

这些限制是刻意保留的。当前版本优先保证资源顺序、Session 收口和厂家 DLL 安全。
