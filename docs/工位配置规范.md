# PicoATE Station Config JSON

日期：2026-06-26

Station config 用来描述“这个工站有哪些设备，以及这些设备真实地址是什么”。

它不描述测试流程。

测试流程仍然放在 sequence JSON。

## 1. 为什么需要 Station Config

Sequence JSON 应该写逻辑设备 ID：

```json
{
  "dmm": "DMM1"
}
```

不要把真实 VISA 地址直接写进测试流程：

```json
{
  "visaAddress": "USB0::0x0957::0x0607::MY59001234::INSTR"
}
```

真实地址属于工站，不属于测试流程。

这样换工站、换仪器、换地址时，不需要改 sequence。

## 2. 文件结构

示例见：

```text
examples/stations/basic_station.json
```

基本格式：

```json
{
  "stationId": "bench-01",
  "name": "PicoATE Bench 01",
  "stopOnFailure": true,
  "scanDialogEnabled": true,
  "txtLogEnabled": true,
  "csvReportEnabled": true,
  "xlsxReportEnabled": true,
  "reportOutputDirectory": "",
  "snLength": 12,
  "snPattern": "BTSN*",
  "snAllowedRegex": "^[A-Z0-9]+$",
  "metadata": {
    "site": "lab"
  },
  "devices": [
    {
      "deviceId": "DMM1",
      "deviceType": "DMM",
      "driverId": "fake.dmm",
      "address": "${DMM1_ADDRESS}",
      "lifetime": "Station",
      "options": {
        "defaultFunction": "DCV",
        "nplc": 10
      }
    }
  ]
}
```

## 3. 顶层字段

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `stationId` / `id` | string | 否 | 工站 ID。 |
| `name` | string | 否 | 工站显示名。 |
| `stopOnFailure` | bool | 否 | 默认 `true`。这是工站统一失败策略，同时作用于普通 Step、TestItem 子步骤、父 TestItem 和 Loop 的最终结果。 |
| `scanDialogEnabled` | bool | 否 | 默认 `true`。决定 TEST 模式是否自动弹出扫码框。 |
| `txtLogEnabled` | bool | 否 | 默认 `false`。打开后把界面实时执行日志同步写入 TXT。 |
| `csvReportEnabled` | bool | 否 | 默认 `false`。打开后生成测试结果 CSV。 |
| `xlsxReportEnabled` | bool | 否 | 默认 `false`。打开后生成带表头、筛选、列宽和结果颜色的 XLSX。 |
| `reportOutputDirectory` | string | 否 | 报告根目录。留空时使用 `PicoATE.UI.exe` 同目录下的 `log`。相对路径以 Station 文件目录为基准。 |
| `snLength` | number | 否 | SN 固定字符数，范围 0-256；`0` 表示不限制长度。 |
| `snPattern` | string | 否 | SN 通配规则；`*` 代表任意数量字符，例如 `BTSN*`、`*BTSN*`、`*BTSN`。留空不限制。 |
| `snAllowedRegex` | string | 否 | 作用于完整 SN 的字符正则，例如 `^[A-Z0-9]+$` 只允许大写字母和数字。留空保持旧项目兼容。 |
| `metadata` | object | 否 | 工站元数据。 |
| `devices` | array | 是 | 设备列表。 |

### 3.1 SN 校验与运行变量

Station Config 的 Basic Settings 提供三项可组合规则：

1. `SN Length`：要求固定字符数，`0` 表示不限长度。
2. `SN Pattern`：面向常见产品系列的简单通配规则，区分大小写。
3. `Allowed Characters`：完整正则表达式，常用值为 `^[A-Z0-9]+$`。

三项同时填写时必须全部通过，扫码框才会关闭并启动测试。校验失败会保留扫码框、选中原内容并显示具体原因。
同一个 SN 可以重复测试，UI 不做历史去重。

通过校验的原始 SN 会进入当前 UUT 的独立运行变量：

```text
${sn}
${serialNumber}
${uut.sn}
${uut.serialNumber}
```

业务插件可把这些变量作为写号参数；不同 UUT 之间不会共享或覆盖 SN。

### 3.2 报告输出目录

TXT、CSV 和 XLSX 采用同一套文件名与分类规则：

```text
log/
  20260719/
    PASS/
      SN001.txt
      SN001.csv
      SN001.xlsx
    FAIL/
      SN002.txt
      SN002.csv
      SN002.xlsx
    SN003.txt       # 测试进行中或运行中关闭程序
    SN003.csv
```

- 有扫码 SN 时用 SN 命名；没有 SN 时用当前时间命名。
- 测试开始后立即在日期目录生成 TXT/CSV，TXT 随界面日志实时刷新；XLSX 在测试形成最终结果时生成。
- 最终 Pass 后移动到 `PASS`，最终 Fail、Error、Timeout、Stop 或 Abort 后移动到 `FAIL`。
- 测试中关闭 ATE 工具时不移动也不删除，文件保留在日期目录根部，表示这是一次未完成运行。
- 同名文件已存在时自动增加 `_2`、`_3`，不会覆盖历史文件。

### 3.3 统一失败策略

`stopOnFailure` 是运行时总开关，UI 和 CLI 都由 Core 执行同一套规则：

| 配置 | Failed / Error / Timeout 的处理 |
|------|---------------------------------|
| `true` | 当前节点 Retry 用尽后停止本 UUT；TestItem 跳过剩余子步骤，随后执行 Cleanup。 |
| `false` | 当前节点 Retry 用尽后继续；TestItem 继续执行剩余子步骤，父项汇总最严重结果，外层流程也继续。 |

- Retry 永远先执行，只有最终一次仍未通过时才应用工站策略。
- “继续”只改变流程是否推进，不会把失败结果改成通过；最终报告和良率仍按真实结果计算。
- 后续步骤若引用失败步骤的输出，会运行并得到明确的变量解析 `Error`；再后面的无关步骤仍可继续。
- 用户 Stop、Abort、Cancelled 不受“失败继续”影响，始终停止。
- While 的 `iterationErrorPolicy` 先处理循环内部本轮行为，Loop 最终结果再交给工站策略。
- Sequence 里旧的 `errorPolicy` 字段仍可读取；加载了 Station 配置后，工站策略覆盖其中的停止/继续选择。

默认 `StationSystem.json` 预留 `CAN1/CAN2`、`PPS1/PPS2`、`DMM1/DMM2`、
`SCOPE1/SCOPE2` 八个常用逻辑设备。它们默认 `enabled=false`，驱动和地址为空，
因此不会连接硬件，也不会触发缺少驱动的校验。项目使用某个槽位时，填写插件型号、
地址和选项后再明确启用。已有工站文件不会在打开时被自动补齐或覆盖。

## 4. Device 字段

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `deviceId` / `id` | string | 是 | 逻辑设备 ID，例如 `DMM1`、`CAN1`、`PSU1`。 |
| `deviceType` / `type` | string | 否 | 设备类型，例如 `DMM`、`CAN`、`PSU`。 |
| `driverId` / `driver` | string | 是 | 设备 session factory ID，例如 `keysight.34465a.visa`。 |
| `address` / `visaAddress` | string | 否 | 真实地址，例如 VISA 地址、IP、串口名、DLL 配置路径。 |
| `lifetime` | string | 否 | `Step`、`Run`、`Station`，默认 `Station`。 |
| `options` | object | 否 | driver 专属配置。 |
| `enabled` | bool | 否 | 默认 `true`；`false` 时忽略该设备。 |

## 5. Lifetime

| 值 | 意思 | 适合 |
|----|------|------|
| `Step` | 每次 step 自己打开/关闭 | 纯算法、一次性脚本、便宜无状态动作。 |
| `Run` | 一次运行期间保持连接 | 当前 sequence 独占的设备。 |
| `Station` | 工站级连接，长期保持 | DMM、CAN、电源、夹具、扫码枪等固定设备。 |

大小写、下划线、短横线、空格会被宽松处理。

例如：

```text
station
Station
station_level
```

后续如果需要 `StationLevel` 这种别名，再扩展枚举解析。

当前实现支持的标准值是：

```text
step
run
station
```

## 6. 变量替换

Station config 复用 `VariableResolver`。

支持：

```text
${PROJECT_DIR}
${SEQUENCE_DIR}
显式 variables
环境变量
```

示例：

```json
{
  "address": "${DMM1_ADDRESS}"
}
```

测试里通过：

```cpp
VariableResolverOptions options;
options.variables.insert("DMM1_ADDRESS", "USB0::...");
```

传入解析器。

## 逻辑设备与插件绑定（2026-07-12）

测试流程不应直接写 GCAN、ZLG 等厂家插件 ID。Sequence 只引用稳定的逻辑设备：

```json
{
  "moduleId": "device",
  "function": "write",
  "inputs": {
    "deviceId": "CAN1.CH1",
    "id": "0x123",
    "data": "01 02 03 04"
  }
}
```

`StationSystem.json` 负责决定 `CAN1` 当前使用哪个插件：

```json
{
  "deviceId": "CAN1.CH1",
  "deviceType": "CAN",
  "physicalDeviceId": "CAN1",
  "channelId": "CH1",
  "driverId": "plugin.can.gcan",
  "timeoutMs": 6000,
  "lifetime": "Run",
  "enabled": true,
  "options": {
    "deviceType": 0,
    "deviceIndex": 0,
    "channelIndex": 0,
    "bitrate": 500000
  }
}
```

- `driverId` 对应 `plugins/PluginRegistry.json` 中的 `moduleId`。
- Station 不再保存 `pluginPath`；DLL 相对路径只在统一注册表中维护。
- `timeoutMs` 是该设备插件单次调用的默认超时。
- `options` 是连接该型号设备时自动补充的固定参数。
- 更换 GCAN/ZLG 等型号时，优先只修改 Station 绑定；Sequence 中的 `CAN1.CH1`、`CAN1.CH2` 和业务流程保持不变。
- Flow Editor 按通道显示 `Send [CAN1.CH1]`、`Send [CAN1.CH2]` 等明确目标，拖入后写入对应的 `deviceId`。

### 统一插件目录

应用目录固定使用以下结构：

```text
PicoATE.UI.exe
PicoATE.NativeHost.exe
StationSystem.json
plugins/
  PluginRegistry.json
  PicoATE.CAN.GCAN.dll
  PicoATE.CAN.CX.dll
  厂家运行库.dll
```

`StationSystem.json` 只保存 `driverId`，不再为每台设备重复保存 DLL 路径：

```json
{
  "pluginRegistry": "plugins/PluginRegistry.json"
}
```

注册表中的 `dll` 必须相对注册表文件保存。旧 Station 中的 `pluginPath` 会在加载时移除；
`options.address`、`options.visaAddress` 会迁移到设备顶层 `address`，运行时只认顶层地址。

### 挂测配置

```json
{
  "loopTestEnabled": true,
  "loopTestCount": 100
}
```

- 关闭时完整流程执行 1 次。
- 打开时使用新的 ExecutionSession 完整执行指定次数，各轮不会复用节点状态。
- 每轮都包含 Setup、Main 和 Cleanup；某轮失败不会阻止下一轮，人工 Stop 会停止后续轮次。
- 最终报告累计各轮 Attempt 和 Measurement，实时事件序号在整个挂测期间保持递增。

## CAN 物理设备与通道模型（2026-07-16）

CAN 配置明确区分“物理盒子”和“可执行通道”：

```text
CAN1                 物理 CAN 盒
  CH1 -> CAN1.CH1    第 1 路运行时端点
  CH2 -> CAN1.CH2    第 2 路运行时端点
CAN2
  CH1 -> CAN2.CH1
  CH2 -> CAN2.CH2
```

约束如下：

- Devices 页面以树形展示物理设备和通道。
- `Type`、`Driver / Model`、`Lifetime`、`Enable` 在 Devices 页面直接配置。
- CAN 物理设备选择一次插件型号，型号绑定会同步到其 CH1/CH2。
- CH1/CH2 是固定通道，不能单独删除；不使用的通道直接设为 OFF。
- Sequence 只引用端点 ID，例如 `CAN1.CH2`，不会引用厂家名。
- `channelIndex` 由框架根据 CH1/CH2 自动维护，右侧参数页不允许手工修改。
- 旧配置中的 `GCAN_CAN1`、`GCAN_CAN2`、`CX_CAN1` 等标识，在 Admin 加载时会迁移为 `CANx.CH1/CH2`，并同步修改 Flow 中的引用。

Station JSON 仍保持扁平 `devices[]`，方便 Core 和现有运行时直接消费：

```json
{
  "deviceId": "CAN1.CH1",
  "deviceType": "CAN",
  "physicalDeviceId": "CAN1",
  "channelId": "CH1",
  "driverId": "plugin.can.gcan",
  "enabled": true,
  "options": {
    "deviceIndex": 0,
    "channelIndex": 0,
    "bitrate": 500000
  }
}
```

## Admin 参数编辑规则（2026-07-16）

右侧 Device Parameters 只保留当前设备的基础连接参数：

- Address 和 Timeout 属于通用参数。
- 插件 `open/connect` 功能的 `PicoATE_Describe.inputs` 用于生成型号参数。
- `enum` 显示为下拉框。
- `boolean` 显示为 OFF/ON 开关。
- `integer/number` 显示为数值控件，并应用 minimum/maximum。
- 只有无法预定义的字符串或十六进制数据才使用文本框。
- `deviceId`、`channelIndex`、`libraryPath` 等框架字段不会出现在右侧。
- 修改只进入文档草稿，最终仍以 `Ctrl+S` 保存到 `StationSystem.json`。

## Station 设备连通性验证（已实现基础版）

Station Config 已提供 `Test Connection`。测试使用当前内存中的 Station 草稿，不要求工程师先保存文件，
也不会由 UI 直接加载厂家 DLL。

当前调用链：

```text
Station Config
  -> CoreExecutionService::testDeviceConnection()
  -> Plugin/DeviceSessionManager
  -> openSession
  -> isHealthy
  -> closeSession
```

连接测试在工作线程执行，支持超时、取消、插件注册失败、设备打开失败、健康检查失败和关闭失败反馈。
结果显示在 Station 诊断区域。它用于提前发现 Driver、DLL 路径、设备索引、通道和基础连接参数错误。

基础连接成功只表示驱动和设备会话可以建立，不代表 CAN 总线接线、收发回环或完整业务协议一定正常。
需要 `getIdentity`、CAN Send/Read、Modbus 寄存器读取等业务级验证时，可以在后续增加
`probe/` Sequence；这类 Probe 复用普通执行引擎和插件函数，不新增专用 ABI。

## 新设备草稿与 Enable（2026-07-22）

- 新增设备后，可先在右侧选择 Type、Driver 和通道，再直接在表格打开 Enable。
- 保存时会把表格中的 Enable 状态与右侧尚未提交的设备草稿合并，生成的逻辑通道不会重新变回失能。
- CAN 物理设备的 CH1/CH2 可独立启用，逻辑 ID 由系统生成并只读，例如 `CAN1.CH1`、`CAN1.CH2`。
- Station 页的修改以草稿形式保留，最终仍由 `Ctrl+S` 或保存按钮统一写入 `StationSystem.json`。
