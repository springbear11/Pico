# PicoATE 插件自描述与统一注册表

日期：2026-07-11

## 1. 目标

Admin 流程编辑器不再要求每个业务 DLL 旁边维护一份功能 Manifest。插件通过
`PicoATE_Describe` 说明自己有哪些功能、哪些参数必填或选填，以及会输出什么结果。

Admin 点击“Scan Plugins”后：

1. 递归扫描 `plugins/` 及其子目录中的 `PicoATE.*.dll`。
2. 每个 DLL 都由独立的 `PicoATE.NativeHost.exe` 加载。
3. NativeHost 调用 DLL 的 `PicoATE_Describe`，UI 进程不直接加载插件。
4. 合法结果集中保存到 `plugins/PluginRegistry.json`。
5. 正常启动和切换设备型号时读取缓存，不重复加载 DLL。

`*.picoate-plugin.json` 和 `pluginId` 已移除，避免 DLL 描述与旁车文件不一致。

## 2. 一个 DLL 的边界

一个 PicoATE 插件 DLL 对应一个具体设备实现或一种明确的业务能力：

```text
PicoATE.CAN.GCAN.dll  -> 广成 CAN 实现
PicoATE.CAN.ZLG.dll   -> 周立功 CAN 实现
PicoATE.CAN.CX.dll    -> 创芯 CAN 实现
```

公共 `ICanAdapter`/`VirtualCanPlugin` 只统一 C++ 接口，不负责向 UI 汇总所有厂商。
每个 DLL 的 `PicoATE_Describe` 只描述当前 DLL 自己能够执行的功能和参数。

## 3. DLL 导出入口

```cpp
extern "C" __declspec(dllexport)
int PicoATE_Execute(const char* requestJsonUtf8,
                    char* responseJsonUtf8,
                    int responseBufferSize);

extern "C" __declspec(dllexport)
int PicoATE_Describe(char* descriptionJsonUtf8,
                     int descriptionBufferSize);

extern "C" __declspec(dllexport)
int PicoATE_GetAbiVersion();
```

- `PicoATE_Execute` 执行业务功能。
- `PicoATE_Describe` 只返回静态 JSON，不连接设备、不创建句柄。
- `PicoATE_GetAbiVersion` 用于 Host 阻止不兼容 DLL；当前返回 `1`。

## 4. 精简描述格式

顶层只要求三个字段：

```json
{
  "name": "GCAN USB-CAN",
  "category": "CAN",
  "functions": []
}
```

| 字段 | 必填 | 用途 |
|------|------|------|
| `name` | 是 | UI 中的具体型号/插件名称 |
| `category` | 是 | 归类到 CAN、DMM、VISA、Modbus 等 |
| `functions` | 是 | 当前 DLL 提供的非空功能数组 |

不要求插件填写 vendor、pluginId、moduleId、schemaVersion。扫描器根据 DLL 相对路径生成
内部 `moduleId`，DLL 路径和 ABI 版本由统一注册表保存。

## 5. 功能和参数

```json
{
  "id": "write",
  "name": "Send CAN Frame",
  "description": "Transmit one CAN frame",
  "timeoutMs": 2000,
  "inputs": [
    {"key": "id", "name": "CAN ID", "type": "string", "required": true, "default": "0x123"},
    {"key": "data", "name": "Frame Data", "type": "hex-bytes", "required": true}
  ],
  "outputs": []
}
```

功能至少填写 `id` 和 `name`。参数至少填写 `key`、`name`、`type`、`required`。
`default`、`minimum`、`maximum`、`unit`、`options`、`description` 和 `timeoutMs` 按需填写。
`enum` 参数必须提供非空 `options`。

支持的参数类型为 `string`、`integer`、`number`、`boolean`、`enum` 和 `hex-bytes`。
输出定义用于生成表达式候选，例如 `${step:rx.outputs.dlc}`，不改变 DLL 的真实返回值。

## 6. CAN 型号与逻辑设备

UI 按 `category` 把 GCAN、ZLG、创芯都放入 CAN 类。工站配置使用逻辑设备 ID 绑定具体型号：

```json
{
  "id": "CAN1",
  "category": "CAN",
  "model": "GCAN",
  "plugin": "PicoATE.CAN.GCAN.dll"
}
```

Sequence Step 调用 `CAN1 + write`，不在每个 Step 重复选择厂商。把 CAN1 从 GCAN 换成
ZLG 时，编辑器从 `PluginRegistry.json` 读取 ZLG 的参数描述并刷新右侧面板：同名参数保留，
不支持的参数隐藏，新增参数使用默认值；缺少默认值的新增必填参数必须重新配置。

型号切换不重新调用 `PicoATE_Describe`。只有新增或升级 DLL 后才重新扫描。

## 7. 统一 PluginRegistry.json

注册表由扫描器生成，不要求工程师手写：

```json
{
  "plugins": [
    {
      "moduleId": "plugin.can.gcan",
      "dll": "PicoATE.CAN.GCAN.dll",
      "abiVersion": 1,
      "description": {
        "name": "GCAN USB-CAN",
        "category": "CAN",
        "functions": []
      }
    }
  ]
}
```

单个插件缺少导出、描述超时、返回非法 JSON 或 ABI 不兼容时，只记录该插件错误；其余合法
插件继续进入注册表。扫描过程不得调用 Open/Connect，也不依赖真实硬件在线。

## 8. 当前实现

- GCAN、CX、HDM3000、Keysight 34410A 和 KORAD DLL 均已导出 Execute、Describe 和 ABI Version。
- NativeHost 已支持一次性 `--describe --dll <path>`。
- PluginCatalog 只扫描 DLL 自描述，并生成统一注册表。
- 支持递归发现、隔离扫描、单插件失败隔离、注册表原子保存和重新加载。
- Admin Flow Editor 工具栏和 Tools 菜单已加入“Scan Plugins”。
- Flow Editor 左侧按“类别 -> 具体插件 -> 功能”显示注册表中的全部功能，不依赖
  Station 是否已经配置设备。
- 功能可以拖入 Setup/Main/Cleanup 或 TestItem/Loop，自动生成编号并进入 Undo/Redo。
- 右侧根据描述生成必填/选填参数、枚举、布尔和数值范围编辑；高级 Inputs JSON 继续保留。
- 未选择目标设备时仍展示全部插件能力；设备类插件必须先选择 Station 目标设备才能拖入，
  不属于仪器设备的算法、文件处理等业务插件可以直接生成调用。

## 与工站逻辑设备的关系

选择了 Station 目标设备时，编辑器生成逻辑设备调用：

```json
{
  "moduleId": "device",
  "function": "read",
  "inputs": { "deviceId": "CAN1" }
}
```

属性编辑器会通过 `CAN1 -> driverId -> PicoATE_Describe` 找回对应参数描述，因此仍可动态展示必填、选填、默认值和枚举项。这样换设备厂家不要求重写测试流程。

未选择目标设备时，Flow 左侧仍展示所有插件，便于工程师查看完整能力。拖入时按插件类别判断：

- CAN、DMM、PSU、SCOPE、SERIAL、MODBUS 等设备类插件必须先选择兼容的 Station 设备或通道；
- 算法、数据处理、文件操作等非设备插件保留自己的 `moduleId`，不写 `inputs.deviceId`，可直接拖入；
- 选择目标设备后，只展示与目标设备类别匹配的插件功能，Basic Functions 始终可用。

## 9. Flow 参数控件规则

Flow Editor 的正常配置路径由 `PicoATE_Describe.functions[].inputs` 驱动：

- `enum` 显示下拉框，插件应提供稳定的 `value` 和给工程师看的 `label`；
- 必填或带默认值的 `boolean` 显示 ON/OFF 开关；
- 可选且没有默认值的 `boolean` 显示“未设置 / ON / OFF”；
- `integer`、`number`、`string`、`hex-bytes` 使用填空，并继续支持 `${expression}`；
- `minimum`、`maximum`、`unit`、`required` 和 `default` 直接用于提示、校验和默认值；
- 逻辑设备步骤额外显示 `Target device` 下拉框，只列出 Station 中支持当前功能的设备或通道。
- `function` 使用 Describe 中的功能列表生成只读下拉框；切换 Module 或目标设备时立即刷新选项。
- 旧脚本中的 Function 如果已经不在当前 Describe 中，界面会标记为不可用并保留原值，等待工程师明确修正，不会静默替换。

`inputs.deviceId` 由目标设备选择器填写，不要求插件在每个功能的 Describe 中重复声明。
`inputs` 和 `parameters` 的原始 JSON 仍然保留，以兼容旧脚本、厂家特有扩展和暂未描述的字段；
它们被收进折叠的 `Advanced JSON`，不会作为普通工程师的默认配置方式。未知字段保存时必须原样保留。

插件新增可配置参数时，应优先更新 `PicoATE_Describe.inputs`，不要要求项目工程师直接编辑
`parameters` JSON。完全由框架实现的 Wait、Limit 等基础功能使用各自的类型化编辑器，字段全部可识别时不显示 Advanced JSON。

## 10. Execute 响应与测量显示

`PicoATE_Execute` 的 `outputs` 用于后续 Step 表达式引用；`measurements` 用于 UI、TXT、
CSV/XLSX 和最终报告。二者可以同时返回，不能用日志代替结构化结果。

通用测量字段：

```json
{
  "name": "CAN_RX_FRAME",
  "value": "ID=0x199 | MASK=0x7FF | DATA=09 01 03 07 | DLC=4",
  "displayLower": "ID=0x199 | MASK=0x7FF",
  "displayUpper": "ID=0x199 | MASK=0x7FF",
  "status": "Passed"
}
```

- `value` 显示在 Actual，并进入 CSV/XLSX 实测值。
- 数值测量优先返回 `lowerLimit`、`upperLimit` 和 `unit`。
- 不能自然表示为单个数值上下限的协议条件，可以返回 `displayLower` 和
  `displayUpper`。这两个字段是通用 UI/报告约定，不限于 CAN。
- CAN 公共 Bridge 负责组合 ID、Mask、Data 和 DLC；GCAN/CX 厂商 Adapter 只负责调用
  厂商 API，不重复实现显示规则。
- 插件日志用于实时诊断；`outputs` 和 `measurements` 才是可被流程和报告消费的正式数据。
